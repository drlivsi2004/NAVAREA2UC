---
name: Offshore operational semantics
description: Domain rule for distinguishing offshore work/deployment notices from messages that define navigational geometry.
---

An offshore notice should be modeled as an operation first when its coordinates are vessel positions, deployment points, work limits, or source-reference points rather than vertices of a navigational object. Anchor spreads, mooring deployments, tows, rig moves, and similar activity notices must not be converted into inferred polygons or connecting lines without explicit source wording.

**Why:** Historical NAVAREA messages repeatedly use the same operational vocabulary with different geometry semantics. Many pipeline, cable, drilling, and seismic notices explicitly define areas or tracklines, but launch/deployment and movement notices often provide disconnected points or only a current position. Treating every coordinate list as a shape creates false geometry and can produce self-intersections.

**How to apply:** Preserve operation type, time window, vessels, berth/clearance, and raw coordinate roles separately. Use Area/Line/Route/Point/AtoN only when the notice explicitly defines that geometry; otherwise retain unconnected source-reference points and flag the operation as semantically unresolved.

For the first compatible release, add semantic metadata and a geometry-status gate before geometry handlers; defer a full OperationObject until structured operation data must be queried, partitioned, or projected separately from existing Furuno objects.

**Why:** The current message model already carries metadata and the Furuno XML exporters only know Area/Line/Circle/Label-style objects. A metadata-first change can stop unsafe inference without an XML schema migration, while a full object would require changes across counting, partitioning, exporting, and tests.

**How to apply:** Treat `semantic_mode` and `geometry_status` as orthogonal: mode says whether operation or geometry has precedence, while status says how strongly coordinates are evidenced. Fields alone are insufficient; operation-first classification must run before area/line handlers.

Explicitly named offshore operational groups may be preserved as one semantic
point label per group when their coordinate sets are not valid navigational
polygons. Do not emit a rejected polygon or reinterpret those groups as
platform objects merely to retain geometry counts.

**Why:** Launch and anchorage-line notices can publish several operational
limits whose coordinates self-intersect or describe disconnected work areas.
The group names and source coordinates remain useful even when a Furuno Area
cannot represent them safely.

**How to apply:** Keep the group name and full coordinate context in the
description, anchor the label to a source coordinate, and keep the result
out of Area/Line/Circle geometry counts.

An explicit `TOW` / `TUG ... TOWING` notice that says `BETWEEN` followed by
two published positions expresses a route intent, but does not by itself
define the route geometry. A straight segment between the endpoints must not
be presented as a safe coastal route.

**Why:** A NAV Station visual reference (not Furuno) for NAVAREA V 589/25 and
593/25 shows a route with intermediate coastal-following points, while the
NAVAREA text provides only endpoints. NAV Station is a separate platform with
its own route engine, so its rendered path cannot be reconstructed from the
two source coordinates alone.

**How to apply:** Recognize the two-position TOW pattern as a route request,
preserve the endpoint order and full operation Description, and emit route
geometry only when verified intermediate points come from a route source or
ENC router. Treat the NAV Station image as cross-platform semantic evidence,
not as physical Furuno verification.

For release 1.3.0, the safe unresolved-route representation for the four
Brazil TOW controls (`V 527/26`, `V 528/26`, `V 589/25`, and `V 593/25`) is
exactly two endpoint Labels with `OPERATION_ONLY` status and no Line, Area, or
Circle. The coastal route remains a future route-source/ENC-routing decision.

**Why:** The source notices publish only endpoints, while the NAV Station
reference supplies a route generated by another platform. A single Furuno
Point is an old physical artifact, not the approved 1.3.0 contract; a straight
endpoint Line would falsely imply a safe route.

**How to apply:** Keep the two Labels in the 1.3.0 release and retest the
current build physically. Do not add route geometry until verified intermediate
points or an approved coastal routing source exists.

For genuine movement of a non-AtoN object described with two published
positions (`MOVED`, `RELOCATED`, `TOWED`, or tug-assisted `FROM ... TO`), emit
the two endpoint points without an inferred connecting line. Relocations of
buoys, beacons, and other AtoN remain in the dedicated AtoN semantics.

**Why:** The same `FROM ... TO` wording can describe either a movable offshore
object or a change to an aid to navigation. Only the former belongs to the
endpoint-only towing/movement fallback; conflating them would turn an AtoN
update into a route-like operation.

**How to apply:** Require an object-movement or towing signal, exclude AtoN
vocabulary, preserve source endpoint order, and keep line geometry restricted
to explicit trackline/route evidence.

Some notices are genuine composite packages: an explicit linear object
(pipeline, cable, trackline, or route) can be marked by separate endpoint
objects such as buoys, beacons, towers, lights, platforms, or other AtoN.
Repeated endpoint coordinates in the Line and point Labels are intentional
because they represent distinct semantic objects.

**Why:** `NAVAREA IX 7/2026` describes a disposal pipeline together with two
yellow mark buoys at its A/B endpoints. Treating the whole package as one Line
lost one buoy and misclassified the other as a generic line label.

**How to apply:** Detect the explicit line evidence and the endpoint-object
positions independently, emit one Line plus one Label per marked endpoint, and
derive each endpoint's style/color/Danger from its object class. Do not let a
single handler's `return True` suppress valid components in the same source
section.

`NAVAREA V 515/26` (underwater operations / divers working) is not classified
as offshore-activity blue semantics or as a towing case; it remains a normal
informational Point/Label. Its blue appearance in the physical ECDIS screenshot
was an accidental manual edit, not an intended classification.

**Why:** The ECDIS photograph is a manually edited visualization and its blue
appearance must not be generalized to every Santos Oil Field or underwater
operations notice.

**How to apply:** Keep the default informational color and single-point
handling for V 515/26 unless the source later provides an explicit semantic
classification that changes this decision.

Physical Run #96 testing reports that `NAVAREA V 449/26` loses its offshore-operation semantics and appears Orange on Furuno instead of the intended offshore presentation.

**Why:** This is a runtime semantic/color loss, not a geometry failure; the manual blue reference for V 449/26 cannot substitute for generated-output evidence.

**How to apply:** Keep V 449/26 open as a separate offshore semantic regression case. Reproduce the generated object from the Run #96 source/XML, restore only the approved offshore classification, and retest color, Danger, and Description without generalizing the rule to V 515/26.

An `UNLIT` light notice remains an informational Orange/NINFO Point unless the
source also provides a separate danger signal such as Wreck, ADRIFT, AGROUND,
or an explicit keep-clear hazard.

**Why:** The `NAVAREA VIII 806/26` source reports an unlit light but does not
describe a wreck or other danger object; the reviewed ECDIS presentation
correctly keeps the light as an informational point.

**How to apply:** Preserve the light name, position, and `UNLIT` status while
keeping `checkDanger=0`; handle header/context retention independently.

Legacy and Modern exports must share the same object descriptions; Legacy
compatibility is limited to truncating that shared text at 999 characters.

**Why:** The two Furuno formats represent the same imported chart content.
Keeping separate descriptions causes semantic context, including partition
parent context, to disappear from Legacy output.

**How to apply:** Store the complete description on both message and container
objects, let Modern emit it unchanged, and apply `LEGACY_MAX_DESC` only in the
Legacy serializer.

Field evidence from the newer Modern Furuno view shows the imported object's
description and the same object's complete vertex table together, including
later vertex indices. It supports description parity while leaving the
existing Legacy export path untouched.

**Why:** The screenshot visibly combines object styling, description text, and
multi-vertex geometry in the new format. It is evidence for shared description
content, not permission to alter Legacy serialization or ordering.

**How to apply:** Preserve Legacy's format, object logic, and export order.
Change only the shared description source, then validate the Legacy 999
character limit separately from geometry fidelity.

The approved code-side mapping for preparatory offshore anchorage deployment
notices is `RESBL` with `checkDanger=0`, using the narrow
`LAUNCH OF` + `ANCHORAGE LINES` wording pattern. This must not become a
generic offshore rule.

**Why:** `V 449/26` was physically observed as Orange despite the intended
offshore presentation, while `V 515/26` is a separate informational point
case and must remain `NINFO`.

**How to apply:** Assert the mapping for `V 449/26` in XML-side tests and
assert the unchanged `NINFO`/non-danger result for `V 515/26`; reserve Furuno
testing for one final batch EXE.

Channel wording is location context, not line geometry. A notice reporting
lesser/reduced depths at multiple positions should emit independent
informational points unless it contains explicit line evidence such as
`TRACKLINE`, `JOINING`, `ROUTE`, `PIPELINE`, `CABLE`, or `CHANNEL WIDTH`.

**Why:** `VIII 729/26` said that depths below about 6.2 m were reported in a
channel at two positions; the generic word `CHANNEL` had incorrectly promoted
it to a connecting Line.

**How to apply:** Keep line detection evidence-based and let depth-report
patterns enter the multipoint path. Test both the resulting point count and a
nearby genuine channel/route case so removing the context word cannot weaken
real line handling.

The field screenshot is identified as `NAV V 522/26`, not the current
`NAV V 502/26` corpus case. Its source text has four repeated unlabelled
`AREA BOUND BY` clauses, each with four coordinates.

**Why:** The screenshot shows an `AREA BOUND BY` object with at least 17
vertices, while the current V 502 source explicitly says `BETWEEN THE POINTS`
and contains 11 different coordinates.

**How to apply:** Treat the screenshot as evidence for NAV V 522/26's Modern
display and description behavior. Keep each repeated boundary paired with its
own four-point ring; never flatten the four rings into one polygon.
